# Convex Architecture - Billing Module

## Structure du Module Billing

Le module billing suit une **architecture modulaire** avec un fichier de re-export :

```
convex/platform/
├── billing.ts                    # 📦 Re-export file (Public API)
└── billing/                      # 📁 Implementation folder
    ├── plans.ts                  # Plan definitions & features
    ├── subscriptionQueries.ts    # Subscription queries
    ├── clerkBillingSync.ts       # Clerk API sync
    ├── webhooks.ts               # Webhook handlers (internal)
    ├── testSubscription.ts       # Test utilities
    └── README.md                 # Module documentation
```

## ⚠️ Ce n'est PAS une duplication

### `billing.ts` - Fichier de Re-export

**Rôle :** Point d'entrée pour l'API Convex générée (`api.platform.billing.*`)

**Contenu :** Re-exporte uniquement les fonctions **publiques** (queries, mutations, actions)

```typescript
// billing.ts
export { getPlansPublic } from "./billing/plans";
export { getWorkspaceSubscriptionAndUsage } from "./billing/subscriptionQueries";
export { syncSubscriptionFromClerk } from "./billing/clerkBillingSync";
```

### `billing/` - Dossier d'Implémentation

**Rôle :** Contient l'implémentation modulaire du système de billing

**Avantages :**
- ✅ Séparation des responsabilités (plans, queries, sync, webhooks)
- ✅ Meilleure lisibilité (fichiers plus petits)
- ✅ Facilite les tests unitaires
- ✅ Évite les fichiers monolithiques

## Fonctions Publiques vs Internes

### ✅ Publiques (re-exportées dans `billing.ts`)

| Fonction | Type | Fichier | Usage |
|----------|------|---------|-------|
| `getPlansPublic` | query | plans.ts | Récupérer les plans disponibles |
| `getWorkspaceSubscriptionAndUsage` | query | subscriptionQueries.ts | Récupérer l'abonnement d'un workspace |
| `getSubscriptionByClerkUserId` | query | subscriptionQueries.ts | Récupérer l'abonnement par Clerk User ID |
| `syncSubscriptionFromClerk` | action | clerkBillingSync.ts | Synchroniser depuis Clerk API |
| `createTestSubscription` | mutation | testSubscription.ts | Créer un abonnement de test |

### ❌ Internes (NON re-exportées)

| Fonction | Type | Fichier | Usage |
|----------|------|---------|-------|
| `syncSubscription` | internalMutation | webhooks.ts | Appelée uniquement par HTTP actions |
| `getWorkspaceByOwner` | internalMutation | webhooks.ts | Helper interne |
| `autoSyncIfNeeded` | internalMutation | clerkBillingSync.ts | Helper interne |

## Problème Résolu : Fichiers Compilés

### ❌ Problème Initial

Les fichiers compilés TypeScript (`.js`, `.js.map`, `.d.ts`) étaient **commités dans Git**, causant des erreurs de duplication lors de la compilation Convex :

```
X [ERROR] Two output files share the same path but have different contents: out\platform\billing.js
```

### ✅ Solution

1. **Ajout au `.gitignore` :**
```gitignore
# Convex compiled files (generated by Convex, should not be committed)
convex/**/*.js
convex/**/*.js.map
convex/**/*.d.ts
convex/**/*.d.ts.map
!convex/_generated/**
```

2. **Suppression des fichiers existants :**
```bash
find convex -type f \( -name "*.js" -o -name "*.js.map" -o -name "*.d.ts" -o -name "*.d.ts.map" \) ! -path "convex/_generated/*" -delete
```

3. **Résultat :**
```bash
npx convex dev --once
✔ Convex functions ready! (1.62s)
```

## Règles à Suivre

### ✅ À FAIRE

- Créer des sous-dossiers pour les modules complexes (ex: `billing/`)
- Utiliser un fichier de re-export à la racine (ex: `billing.ts`)
- Re-exporter uniquement les fonctions publiques
- Garder les `internalMutation` dans les sous-dossiers

### ❌ À ÉVITER

- Committer les fichiers `.js`, `.js.map`, `.d.ts` (sauf `_generated/`)
- Créer des fichiers monolithiques (> 500 lignes)
- Re-exporter les fonctions internes
- Dupliquer la logique entre fichiers
